# Model scope and limitations

Quantum Collapse is a deterministic dependency-graph scenario model. Its outputs describe what follows from the graph and parameter values supplied to the model; they are not forecasts of when a cryptographically relevant quantum computer will exist or which real organizations would fail.

## What the model represents

- A directed edge `A -> B` means that B depends on A. Cascade propagation follows outgoing edges from compromised seed nodes.
- Each node carries scenario inputs such as its dominant cryptographic label, criticality, and migration percentage.
- Risk scores combine those inputs with the vulnerability weights defined in `backend/quantum_collapse/risk.py`.
- Migration sweeps vary the specified migration input while keeping the remaining scenario assumptions fixed unless the sweep explicitly says otherwise.

## What results do not establish

A modeled failure or risk score does not establish that a real dependency exists, a cryptographic primitive is reachable in deployed code, a service is exploitable, or a future attack is feasible on a particular machine. The graph, criticality values, migration rates, and vulnerability weights are assumptions unless independently sourced for a specific scenario.

The model does not simulate a full cryptanalytic attack, estimate attack runtime, or infer dependency edges from source-code findings. A scanner finding is evidence that a detector matched a supported pattern; it is not proof of runtime reachability.

## Reproducible scenario reports

When publishing a scenario sweep, record at least:

- the exact source revision;
- seed node(s), graph input, migration values, and all non-default model parameters;
- trial count and random seed for any randomized extension;
- the output's measurement type and known limitations.

Keep deterministic model outputs separate from empirical observations. If a result is generated by sampling model inputs, describe its percentiles as scenario-sensitivity percentiles—not as empirical confidence intervals.

## Review checklist for model changes

1. Validate node attributes and parameter ranges at the boundary where inputs enter the model.
2. Add regression cases for invalid inputs, empty inputs, and known graph shapes.
3. Test reproducibility whenever a random seed is supported.
4. Assert mathematical invariants only where the model guarantees them; document cases where topology or other parameters can change the expected direction.
5. Update this document when a change expands the modeled phenomena or changes the interpretation of an output.

## Cryptographic reference

Use the primary NIST publications when describing the finalized post-quantum standards:

- [FIPS 203: Module-Lattice-Based Key-Encapsulation Mechanism Standard](https://csrc.nist.gov/pubs/fips/203/final)
- [FIPS 204: Module-Lattice-Based Digital Signature Standard](https://csrc.nist.gov/pubs/fips/204/final)
- [FIPS 205: Stateless Hash-Based Digital Signature Standard](https://csrc.nist.gov/pubs/fips/205/final)

These publications define standards; they do not validate the scenario's hand-set risk weights or topology.
